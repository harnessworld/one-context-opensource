# Contributing to one-context

Thanks for your interest. one-context is a young project in beta —
we welcome focused contributions with reproducible checks and clear documentation.

## What belongs here

Framework-generic improvements only:

- CLI behavior, adapters, validation, context export, sync/worktree,
  skills machinery, docs, and samples.
- Anything reproducible on a fresh clone without private repositories,
  personal provider configuration, or machine-specific routes.

Private workspaces (personal knowledge, business bindings, provider
setup) intentionally do not live here. If your change only makes sense
with external repositories or credentials, it is out of scope.

## Development setup

```bash
git clone https://github.com/harnessworld/one-context-opensource.git one-context
cd one-context
python3 -m venv .venv            # Windows: py -m venv .venv (launcher only)
source .venv/bin/activate        # Windows: .venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e "./packages/one-context[dev]"
```

Supported interpreters: Python 3.10 – 3.14. CI exercises 3.10 and 3.12
on Linux, plus 3.12 on macOS and Windows.

## Everyday checks

Run these before opening a PR (CI runs them too):

```bash
# from the repository root
onecxt doctor                    # manifests, knowledge refs, feature index
onecxt adapt dev                 # regenerate tool surfaces
onecxt adapt dev --check         # surfaces must be in sync

# package tests run from the package directory
(cd packages/one-context && pytest)
```

Notes:

- Tests marked `slow` talk to real LLMs and are excluded by default; run
  them deliberately with `pytest -m slow` from `packages/one-context`.
- Never commit secrets, `.env` files, `.onecxt/local.yaml`, or anything
  from a private workspace. The review checklist in the PR template
  repeats this deliberately.

## Change flow

1. Open (or find) a GitHub issue; agree on the approach for non-trivial
   changes before coding.
2. For non-trivial changes, follow the sample feature flow: copy
   `features/_template/` to `features/<category>/<feature-id>/`, fill in
   spec and design, register in `INDEX.md`. Trivial fixes may skip this.
3. Implement. Canonical sources are `meta/*.yaml`, `.onecxt/RULES.md`,
   `knowledge/01_Compiled/**`, `features/`, and `skills/<name>/SKILL.md`.
   Generated files (marked `GENERATED by onecxt adapt`) must only change
   via `onecxt adapt`.
4. Update docs touched by the change (`README.md`, `README.zh-CN.md`,
   `docs/**`) and `CHANGELOG.md` (Unreleased section).
5. Push a PR; use the PR template. Keep commits focused; reference the
   issue (`Fixes #N`).

## Code style

- Match the surrounding code; the package targets Python 3.10 (`from
  __future__ import annotations` is used).
- Tests live under `packages/one-context/tests/`; prefer extending an
  existing module over inventing new ones.
- Adapters: one public module per tool under `one_context/adapters/`;
  shared behavior belongs in `_*.py` helpers.
- User-facing CLI text stays plain and machine-parseable where tests
  assert on it.

## Reporting issues, security

- Bugs and requests: use the GitHub issue forms (`.github/ISSUE_TEMPLATE/`).
- Vulnerabilities: do **not** open public issues — see
  [SECURITY.md](SECURITY.md).
